---
title: "Running inside a shared database"
description: "Keep Open Wearables in its own schema and role inside a PostgreSQL database it does not own"
---

By default Open Wearables expects a database of its own and creates its tables in `public`. If you would rather keep it inside an existing database — so one backup covers it, or so a delete can span your data and its data in one transaction — give it a **schema** and a **role** of its own.

<Warning>
The schema isolates names. The **role** is what isolates privileges: a role that owns only this schema cannot create, alter or read anything else, so a mistake in configuration fails with a permission error instead of writing into another schema.
</Warning>

## Settings

| Variable | Default | Meaning |
|----------|---------|---------|
| `DB_SCHEMA` | `public` | Schema for Open Wearables' tables. Any value other than `public` sets `search_path` on every connection and keeps alembic's `alembic_version` table in that schema. Must be a lowercase identifier. |
| `DB_POOL_SIZE` | `20` | Connection pool size **per process** — the API, each Celery worker, beat and flower each hold one. |
| `DB_MAX_OVERFLOW` | `30` | Extra connections per process beyond the pool. |

`DB_USER` and `DB_PASSWORD` are the role below. Size the pool against the database's `max_connections`, which the other applications on it share.

## Create the role and the schema

Run as a user that may create roles, in the shared database. The password comes from your secret store; never type it into the command line.

```sql
-- psql -v ow_password="$OPEN_WEARABLES_DB_PASSWORD" -d yourdb -f this-file.sql
CREATE ROLE open_wearables LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE
  PASSWORD :'ow_password';
CREATE SCHEMA openwearables AUTHORIZATION open_wearables;

-- Optional, and database-wide: PostgreSQL grants USAGE on `public` to PUBLIC,
-- so the role can still see names there. Revoke it only if every other role
-- that needs `public` holds USAGE explicitly.
-- REVOKE USAGE ON SCHEMA public FROM PUBLIC;
```

Then set `DB_SCHEMA=openwearables`, `DB_USER=open_wearables` and its password, and start the stack. Migrations create every table inside `openwearables`, owned by `open_wearables`.

What changes in schema mode:

- the migration environment creates the schema only if it is missing, so the role needs no `CREATE` privilege on the database when the schema already exists;
- `scripts/init/create_svix_db.py` does not try to create svix's database — create it separately, with a role of its own;
- the storage estimate on the data-lifecycle settings counts only this schema's tables.

## Verify

```sql
-- every table it created is in its schema, and it owns them
SELECT schemaname, count(*) FROM pg_tables
 WHERE tableowner = 'open_wearables' GROUP BY 1;

-- no foreign key crosses the schema boundary, in either direction
SELECT count(*) FROM pg_constraint c
  JOIN pg_class r ON r.oid = c.conrelid
  JOIN pg_class f ON f.oid = c.confrelid
 WHERE c.contype = 'f'
   AND r.relnamespace <> f.relnamespace
   AND 'openwearables'::regnamespace IN (r.relnamespace, f.relnamespace);

SELECT version_num FROM openwearables.alembic_version;
```

## Granting another application access

Grant only what that application needs, table by table. For example, a service that deletes a user's data here as part of its own erasure:

```sql
GRANT USAGE ON SCHEMA openwearables TO erasure_role;
-- `DELETE ... WHERE id = ...` reads `id`, so DELETE alone is refused
GRANT SELECT (id), DELETE ON openwearables."user" TO erasure_role;
```

That is the whole grant: every table that references `user` does so with `ON DELETE CASCADE`, and the cascade runs with the owning role's privileges, so deleting the user removes its connections, data sources and everything under them without any grant on those tables.

Open Wearables' role needs nothing on the other schemas.

## Backups and restores

A `pg_dump` of the database includes the schema. Create the role before restoring, and prefer a dump that keeps ownership. A dump taken with `--no-owner --no-privileges` restores every object as the restoring user; give them back before starting the stack — tables carry their indexes and sequences with them, and the migrations create one enum type:

```sql
ALTER SCHEMA openwearables OWNER TO open_wearables;
DO $$
DECLARE r record;
BEGIN
  FOR r IN SELECT oid::regclass AS name FROM pg_class
            WHERE relnamespace = 'openwearables'::regnamespace AND relkind IN ('r', 'p') LOOP
    EXECUTE format('ALTER TABLE %s OWNER TO open_wearables', r.name);
  END LOOP;
  FOR r IN SELECT oid::regtype AS name FROM pg_type
            WHERE typnamespace = 'openwearables'::regnamespace AND typtype = 'e' LOOP
    EXECUTE format('ALTER TYPE %s OWNER TO open_wearables', r.name);
  END LOOP;
END $$;

-- nothing in the schema is owned by anyone else
SELECT count(*) FROM pg_class
 WHERE relnamespace = 'openwearables'::regnamespace
   AND relowner <> 'open_wearables'::regrole;
```

## Limits

- **Extensions.** Open Wearables' migrations create or alter no extension. Extensions are database-wide, so re-check this when upgrading; a non-superuser role turns a future `CREATE EXTENSION` into a permission error rather than a silent change.
- **Downgrades** reverse to `cc39513098b0`. Below it, earlier migrations drop unnamed constraints and cannot run in reverse.
- **Offline mode** (`alembic upgrade --sql`) cannot reach head: `b2c3d4e5f6a1` inspects a live connection.
